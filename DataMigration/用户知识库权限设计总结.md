# 用户知识库权限设计总结

## 1. 问题分析

原系统设计中，知识库（KnowledgeBase）与用户（User）之间缺乏明确的所有权和访问权限关系。这导致无法实现以下需求：
- 每个用户可以看到和管理自己的私有知识库
- 所有用户可以访问公共知识库
- 用户可以共享知识库给其他用户，并设置不同权限级别

## 2. 解决方案设计

采用多对多关系模型，通过中间表 `UserKnowledgeBase` 实现用户与知识库的权限管理。

### 2.1 核心概念

1. **所有者（Owner）**：知识库的创建者，拥有完整的管理权限
2. **公共知识库（Public KnowledgeBase）**：所有用户可见的知识库
3. **私有知识库（Private KnowledgeBase）**：只有所有者或授权用户可见的知识库
4. **访问权限级别（AccessLevel）**：控制用户对知识库的操作权限

### 2.2 实体关系图

```
User (1) ──── (n) UserKnowledgeBase (n) ──── (1) KnowledgeBase
                │
                └── AccessLevel (enum)
```

## 3. 实体修改详情

### 3.1 KnowledgeBase 实体修改

**新增字段：**
- `OwnerId` (Guid?)：所有者用户ID，可为空（系统知识库）
- `Owner` (User?)：所有者用户导航属性
- `IsPublic` (bool)：是否为公共知识库，默认 false
- `UserAccesses` (ICollection<UserKnowledgeBase>?)：用户访问权限关系

**作用：**
- `OwnerId` 确定知识库的所有者
- `IsPublic` 控制知识库的可见性
- `UserAccesses` 管理其他用户的访问权限

### 3.2 User 实体修改

**新增导航属性：**
- `AccessibleKnowledgeBases` (ICollection<UserKnowledgeBase>?)：用户可访问的知识库权限关系

**作用：**
- 通过此属性查询用户可以访问的所有知识库

### 3.3 新增 UserKnowledgeBase 实体

**字段定义：**
- `Id` (Guid)：主键
- `UserId` (Guid)：用户ID
- `KnowledgeBaseId` (Guid)：知识库ID
- `AccessLevel` (KnowledgeBaseAccessLevel)：访问权限级别
- `User` (User)：用户导航属性
- `KnowledgeBase` (KnowledgeBase)：知识库导航属性

**权限级别枚举（KnowledgeBaseAccessLevel）：**
- `ReadOnly` (0)：只读权限，可查看知识库内容
- `ReadWrite` (1)：读写权限，可添加/删除文档
- `Admin` (2)：管理权限，可管理用户权限

## 4. 数据库配置更新

### 4.1 DbContext 更新

1. **新增 DbSet：**
   ```csharp
   public DbSet<UserKnowledgeBase> UserKnowledgeBases { get; set; }
   ```

2. **KnowledgeBase 配置：**
   - 添加 `IsPublic` 字段配置
   - 添加与 `Owner` 的关系配置（可为空，级联设置为 SetNull）
   - 添加与 `UserAccesses` 的关系配置
   - 添加 `OwnerId` 和 `IsPublic` 索引

3. **User 配置：**
   - 添加与 `AccessibleKnowledgeBases` 的关系配置

4. **UserKnowledgeBase 配置：**
   - 表名：`user_knowledge_base`
   - 复合唯一索引：`(UserId, KnowledgeBaseId)` 确保每个用户对每个知识库只有一条权限记录
   - 关系配置：与 User 和 KnowledgeBase 的双向关系
   - 访问权限级别存储为整数（`HasConversion<int>()`）

## 5. 权限查询逻辑

### 5.1 用户可访问的知识库查询规则

1. **公共知识库：** `IsPublic == true` 的所有知识库
2. **自有知识库：** `OwnerId == userId` 的知识库
3. **共享知识库：** 通过 `UserKnowledgeBase` 表关联，`UserId == userId` 的知识库

**查询示例（伪代码）：**
```csharp
var accessibleBases = await context.KnowledgeBases
    .Where(kb => kb.IsPublic ||
                 kb.OwnerId == currentUserId ||
                 kb.UserAccesses.Any(ua => ua.UserId == currentUserId))
    .ToListAsync();
```

### 5.2 权限验证逻辑

在执行操作前验证用户权限：
- **读取操作：** 需要 `ReadOnly`、`ReadWrite` 或 `Admin` 权限
- **写入操作：** 需要 `ReadWrite` 或 `Admin` 权限
- **权限管理：** 需要 `Admin` 权限或所有者身份

## 6. 数据库迁移步骤

### 6.1 生成迁移

```bash
cd DataMigration
dotnet ef migrations add AddKnowledgeBaseUserPermissions --project DataMigration --startup-project PgSqlVectorSearch
```

### 6.2 迁移变更内容

1. **knowledge_base 表新增列：**
   - `owner_id` (uuid, nullable)：所有者用户ID
   - `is_public` (boolean, not null, default false)：是否公共知识库

2. **新建 user_knowledge_base 表：**
   - `id` (uuid, primary key)
   - `user_id` (uuid, not null)
   - `knowledge_base_id` (uuid, not null)
   - `access_level` (integer, not null)
   - 外键约束和索引

3. **新增索引：**
   - `knowledge_base(owner_id)`
   - `knowledge_base(is_public)`
   - `user_knowledge_base(user_id, knowledge_base_id)`（复合唯一索引）

### 6.3 应用迁移

```bash
dotnet ef database update --project DataMigration --startup-project PgSqlVectorSearch
```

## 7. 向后兼容性

### 7.1 现有数据处理

1. **现有知识库处理：**
   - 所有现有知识库的 `OwnerId` 将设置为 `NULL`
   - 所有现有知识库的 `IsPublic` 将设置为 `false`
   - 需要在迁移后手动设置知识库的所有者和可见性

2. **权限迁移建议：**
   - 为系统管理员创建默认权限
   - 重要知识库设置为公共知识库

### 7.2 代码兼容性

- 现有代码中直接访问 `KnowledgeBases` 的地方需要更新权限验证
- 新增的字段均为可空或具有默认值，不会破坏现有功能
